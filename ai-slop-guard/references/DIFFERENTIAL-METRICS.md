# Differential Metrics & Heuristics Reference

Evaluating pull requests and commits generated by AI assistants requires quantitative metrics to distinguish tight, focused solutions from noisy code explosions.

---

## 1. The Differential Churn Ratio

The churn ratio measures how much code was added or modified relative to the actual functional problem being solved.

### Formula:
$$\text{Churn Ratio} = \frac{\Delta \text{Lines Added} + \Delta \text{Lines Deleted}}{\text{Estimated Minimum Functional Patch Size}}$$

### Thresholds:
- **Optimal ($< 1.5$)**: Clean, surgical fix. Touched only the necessary lines.
- **Acceptable ($1.5 - 3.0$)**: Standard refactor with minor import updates and test coverage.
- **Elevated ($3.0 - 5.0$)**: Suspect unnecessary refactoring, opportunistic reformatting, or boilerplate introduction.
- **Critical Slop ($> 5.0$)**: The agent introduced widespread architectural churn, rewrote unrelated functions, or regenerated entire files. **Reject and demand a minimal diff.**

---

## 2. File Spread Index (FSI)

Measures how widely the agent's edits are scattered across the codebase.

### Formula:
$$\text{FSI} = \frac{\text{Total Files Modified}}{\ln(\text{Total Lines Changed} + 1)}$$

### Interpretation:
- A bug fix that touches 1 file and 5 lines is localized and safe ($\text{FSI} \approx 0.55$).
- A bug fix that modifies 12 different files to change 15 lines of logic indicates an agent that chased symptoms across the codebase rather than fixing the root cause in the shared service.

---

## 3. The Re-invention Factor (RIF)

Detects when an agent introduces logic that already exists nearby.

### AST / Token Similarity Check:
When an agent adds a new function `fn_new()`, compute token-level Jaccard similarity against all existing functions in the workspace:

$$J(A, B) = \frac{|A \cap B|}{|A \cup B|}$$

- If $J(\text{fn\_new}, \text{fn\_existing}) > 0.65$: The agent has re-invented an existing utility.
- **Action**: Require the agent to delete `fn_new` and import `fn_existing`.

---

## 4. Comment-to-Code Noise Ratio (CCNR)

AI models are infamous for generating obvious, useless comments that describe what the code is doing syntactically rather than explaining *why*.

### Detection:
Look for comments that match the following AST nodes:
```typescript
// Set status to active (NOISE)
status = 'active';

// Return the result (NOISE)
return result;
```

If comments merely repeat the identifier or keyword, strip them. Real comments explain business constraints, edge-case workarounds, and non-obvious invariants.
